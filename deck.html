The Problem

現實困境：純大語言模型 (LLM) 的三大痛點

即便頂級大模型再強大，本質仍是「文字機率預測器」，直接投入實務會遭遇瓶頸：

🎭 1. 模型幻覺 (Hallucination)

追求語句通順而非事實真偽。面對陌生或未記載的冷門問題時，容易「自信地編造不實答案」。

⏳ 2. 知識截斷 (Knowledge Cutoff)

模型知識凍結在訓練完成的那一天。無法即時知曉最新發布的文件、新聞、股價或伺服器數據。

🔒 3. 缺乏私有資料與溯源

無法讀取企業內部規章或個人筆記；且回答無法指出明確的頁碼或法律條文來源，難以建立信任。

Core Concept

解方誕生：什麼是檢索增強生成 (RAG)？

RAG = 外部檢索系統 (Retrieval) + 大語言模型 (Generation) 的黃金組合。

📖 經典生活比喻：開卷考試 vs. 閉卷死背

  • 純 LLM（閉卷考試）：只能硬背腦袋裡的歷史記憶，記憶模糊就憑直覺瞎猜。
  • RAG 系統（開卷考試）：
    1. 先到資料庫翻閱權威參考書（檢索 Retrieval）；
    2. 找出最關鍵的 3 頁筆記擺在桌上；
    3. 結合大腦語言能力，產出條理清晰的解答（生成 Generation）。

🧠 核心架構思維：解耦 (Decoupling)

參數化記憶（Parametric）：LLM 權重負責邏輯推理與語言表達。
非參數化記憶（Non-parametric）：向量資料庫動態存儲真實事實。

💡 工程價值：更新知識只需修改資料庫，完全不需要重新訓練或微調數十億參數的神經網路！

Architecture

全景鳥瞰：RAG 系統生命週期與處理管道 (Pipeline)

系統運作明確分為「離線索引構建」與「在線即時查詢」兩大生命週期：

1. 文件載入 (Load)
讀取 PDF, Markdown, 網頁
➔
2. 文本切塊 (Split)
切分 Chunk 並保留 Overlap
➔
3. 向量儲存 (Store)
Embedding 轉向量存入 DB
➔
4. 相似檢索 (Retrieve)
查詢向量比對，抓 Top-K
➔
5. 提示生成 (Generate)
注入 Context 給 LLM 作答

📁 離線準備 (Indexing Pipeline)

批次自動化執行：原始文件 $\to$ 切塊過濾 $\to$ 向量計算 $\to$ 建立高速搜尋索引庫。

⚡ 即時查詢 (Query Pipeline)

毫秒級即時互動：提問 $\to$ 向量相似度搜尋 Top-K $\to$ 拼裝 Prompt $\to$ LLM 推理輸出。

Indexing Deep-Dive

步驟拆解一：資料準備與文本切塊 (Chunking)

為什麼長篇大論不能直接塞入模型？文本切塊的工程細節與智慧：

✂️ 為什麼一定要切塊？

  • 向量稀釋問題：整篇萬字報告轉成單一向量，會導致所有核心概念被平均化，檢索完全抓不準。
  • 模型上下文限制：LLM 輸入視窗有限，精簡的 Chunk 才能精確回答問題並節省 Token 成本。

🔗 重疊機制 (Chunk Overlap) 的妙用

若硬生生在第 500 字切斷，正好切在關鍵句中（例如：「本電路最大耐壓為……」在下一塊才出現「12V」），語意會斷裂。

💡 工程實踐：將 10%~20% Overlap 與 500~1000 tokens 作為啟發式起始基準，依任務靈活微調！

依據 Wiki: 02_pipeline.md | 參考來源：Pinecone 切塊工程指引 (raw/source_05.md)
Vector DB & Embedding

步驟拆解二：文字變座標 (Embedding & Vector DB)

如何讓電腦聽懂文字背後的「言外之意」？

📍 向量嵌入 (Vector Embedding)

將文字對應到高維空間（如 1536 維）的數值座標點。在此空間中：

  • 「電動車」與「特斯拉」空間距離極近（語意相近）。
  • 「香蕉」與「單晶片微電腦」空間距離極遠。

🗄️ 為什麼需要「向量資料庫」？

傳統 SQL 資料庫（如 MySQL）擅長精確匹配（`=` 或 `LIKE`），但無法在毫秒內於百萬筆資料中搜尋「幾何距離最近」的點。

ANN 近似最近鄰演算法（如 HNSW） 專門解決高維座標的超高速搜尋難題。

依據 Wiki: 03_vector_db.md | 參考來源：Lewis et al. 及 Pinecone (raw/source_01, 05.md)
Retrieval Phase

步驟拆解三：如何精準撈出答案？(Retrieval)

計算問題向量與資料庫文字塊的幾何關聯：

📐 餘弦相似度 (Cosine Similarity)

衡量兩個高維向量的「夾角方向」：

$\cos(\theta) = \frac{\vec{A} \cdot \vec{B}}{\|\vec{A}\|\|\vec{B}\|}$

數學定義值域為 $[-1, 1]$（文本實務中多數落在 $0 \sim 1$），只衡量方向夾角，不受文字篇幅長短影響。

⚡ 點積運算 (Dot Product)

若向量在儲存前已經完成正規化（單位向量）：

$\text{Score} = \vec{A} \cdot \vec{B}$

運算速度極快，能充分發揮現代硬體矩陣乘法加速。

🎯 Top-K 候選提取

擷取關聯度最高的前 $K$ 篇文本片段（例如 $K=3$）。

$K$ 太小可能遺漏答案；$K$ 太大則容易引入雜訊干擾模型。

依據 Wiki: 03_vector_db.md | 參考來源：Lewis et al. 論文 (raw/source_01.md)
Generation Phase

步驟拆解四：合成解答 (Prompt Augmentation)

生成階段的關鍵：透過精緻的提示詞模板，將檢索資料作為上下文約束 LLM：

📝 典型 RAG 提示詞結構

你是一個專業的技術教學助手。
請嚴格根據以下【參考資料】回答【問題】。
若資料中未提及，請明確回答不知道，切勿捏造！

【參考資料】：
{檢索出的 Top-K 文本區塊內容}

【使用者問題】：
{使用者輸入的問題}

請以繁體中文條理分明作答，並附上段落依據。

🛡️ 雙重防護機制

  • 邊界約束（Groundedness）：明確告知模型「不知道就說不知道」，顯著降低模型憑空捏造的幻覺機率（但仍須防範檢索雜訊或理解偏差）。
  • 引用回溯（Citation）：要求回答標記參考資料編號，讓讀者可隨時檢驗出處真實性。

Advanced Techniques

進階架構：混合檢索 (Hybrid) 與重排序 (Rerank)

面對複雜專利、型號代碼或多文本推理，基礎 RAG 的升級方向：

🔀 混合檢索 (Hybrid Search)

稠密向量（Dense / 語意理解）+ 稀疏關鍵字（Sparse / BM25 精確命中）

  • 解決純向量模型記不住特定晶片型號（如 `STM32F4`）或冷僻字眼的問題。
  • 透過 RRF 演算法融合兩者分數，兼顧理解力與精準度。

🎯 重排序機制 (Reranking)

初試海選（Bi-Encoder 撈 30 篇）$\to$ 深度複試（Cross-Encoder 挑 3 篇）

  • 利用交叉注意力（Cross-Attention）深度重新評分，大幅提升前段命中率。
  • 代價：需承擔額外神經網絡前向推論延遲（Latency）與 GPU 算力開銷。
依據 Wiki: 04_advanced.md | 參考來源：LlamaIndex 與 Pinecone 指南 (raw/source_03, 05.md)
Engineering Decisions

工程決策：何時用 RAG？何時用微調 (Fine-tuning)？

沒有萬能架構，只有最適合情境的工程權衡：

評估維度 檢索增強生成 (RAG) 模型微調 (Fine-tuning)
主要目標 提供動態外部事實知識（即時外掛資料庫） 微調語言風格、特定任務輸出格式或領域行話習慣
知識更新頻率 即時（寫入資料庫立即生效） 緩慢（每次更新皆須收集資料重訓模型）
幻覺抑制 大幅降低（以文本為依據並可溯源；但若檢索錯誤仍可能出錯） 有限（主要依賴權重記憶，無外部約束時仍易產生幻覺）
算力與維護成本 低至中等（標準向量檢索開銷） 極高（需昂貴 GPU 算力與資料標註）

📌 工程結論：查事實、追溯源、動態資料優先選 RAG；調格式、學專業行話選 Fine-tuning。

Evaluation & Summary

品質評估：RAG 三元組 (RAG Triad) 與結語

如何科學地驗證一個 RAG 系統的好壞？

1. 上下文關聯性

Context Relevance

檢索器抓出來的內容，是否真正與問題高度相關？還是混雜了無關廢話？

2. 事實忠實度

Groundedness / Faithfulness

回答中的每個陳述，是否 100% 能在 Context 中找到確鑿證據？嚴防脫稿演出。

3. 回答相關性

Answer Relevance

生成的答案是否直擊痛點、正面回答使用者提問，而不是答非所問？

🚀 總結與展望：

RAG 成功將 LLM 的「語言理解優勢」與「外部精準資料庫」結合，是現代 AI 工程最核心的落地基石。進一步學習可探索 GraphRAG 與 Agentic RAG 自適應檢索流程！
